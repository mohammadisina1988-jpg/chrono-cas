# ChronoCAS: source-grounded streaming linearizability checks

A deployment fixes a source repository and an initial register value. Anyone submits a commit-pinned report for the current round. Leader and validators independently fetch its complete prose and interpret all three clients' calls, intervals, arguments and returns. Validators compare every normalized field exactly and separately audit each full call/window/return clause. Only the accepted interpretation enters the concurrency checker.

Each round has one completed operation from each distinct client a/b/c: READ, WRITE or compare-and-swap (CAS). Register values are 0..3; invocation/response ticks are 0..255. The checker considers all six operation orders from every currently possible register state. An operation whose response tick is strictly earlier than another invocation must precede it. Equal ticks leave order unspecified. Every admissible order is simulated against actual READ/WRITE/CAS semantics. All successful terminal states are retained, rather than choosing one convenient witness. Trial journals include blocked orders and the first semantic failure of every failed execution.

The cursor contains current round, last accepted completion boundary and the complete frontier of possible register states. A successful wave advances all three. The next accepted wave must start strictly after the preceding boundary, making frontier states sufficient to summarize the accepted prefix. A violation, incomplete interpretation or overlapping cut is recorded without advancing. Future rounds cannot skip that slot; a new report for the same round can supply a corrected candidate. Reports are immutable and duplicates are rejected. Corrections are alternative reported candidates, not a claim that previously observed physical behavior changed.

The contract owns report acquisition, interpretation consensus, exhaustive ordering checks, ambiguity-preserving frontier evolution and immutable diagnostics. Clients own report publication, actual operation collection, clock synchronization and UI. There are no service certificates, physical-service-delivery assertions or administrator overrides. These checks establish consistency of published candidate histories with the bounded abstract register model; hashes prove bytes, not reporter honesty. Missing observations are never completed by an invented timestamp or outcome.

This is a streaming concurrent-history auditor, not an owner-controlled graph editing protocol or a renamed signal-filter compiler. The real-time ordering relation is derived from fetched observations; there are no proposed graph edits. Classical linearizability is credited to [Herlihy and Wing (1990)](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf). This implementation checks consistency with the reported partial time order, not hidden ordering inside equal timestamp bins. Pending calls, overlapping rounds, multi-object histories and arbitrary process programs are outside its model.

Bounds: six report records, three clients/operations per round, four register values and at most 24 trial rows per report. Counterfactual views re-evaluate a recorded report from another hypothetical initial value using the same accepted source and cut. Generic CLI transport and test bootstrap are reused under MIT; concurrency semantics, streaming frontier, fixtures and independent prefix-search oracles are new.
